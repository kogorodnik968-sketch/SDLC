## ADR-001: Серверная часть на Java и Spring Boot

- status: accepted
- date: 2026-11-07
- decision-makers: Огородник Е.В. (архитектор)
- consulted: Заказчик (роль в ролевой игре)
- informed: преподаватель

### Контекст и постановка задачи

Нужно выбрать технологию для серверной части платформы Siadziba: она должна обрабатывать заявки и брони, работать с базой данных, отправлять письма, выполнять фоновые задачи (отмена неоплаченных броней) и обеспечивать безопасность (REQ-SEC-001, 003, 005). Вопрос: какой язык и фреймворк использовать?

### Драйверы решения

1. Ограничение SRS (раздел 2.3): серверная часть должна быть написана на Java с использованием Spring Boot.
2. Встроенная поддержка безопасности, работы с базой данных и фоновых задач (REQ-SEC-001, 003, 005, REQ-FUNC-013).
3. Бесплатность инструментов (REQ-COST-001).
4. Простота сборки и запуска (REQ-BUILD-001, REQ-INST-001).

### Рассмотренные варианты

- Java + Spring Boot
- Node.js + NestJS
- Python + Django

### Итог решения

Выбранный вариант: «Java + Spring Boot», потому что это обязательное ограничение SRS, а Spring Security, Spring Data JPA и планировщик задач закрывают основные потребности без дополнительных библиотек.

### Последствия

- Хорошо, потому что безопасность, доступ к базе и планировщик есть «из коробки» и хорошо документированы.
- Хорошо, потому что приложение собирается в один JAR-файл и запускается одной командой.
- Плохо, потому что Spring Boot требует больше настроек и времени на старт, чем более лёгкие фреймворки.
- Плохо, потому что для запуска нужна установленная Java (версии 17 и выше).

### Подтверждение

Соблюдение решения проверяется инспекцией репозитория: наличие проекта Maven со Spring Boot, успешная сборка одной командой (REQ-BUILD-001) и запуск по инструкции README (REQ-INST-001).

### Плюсы и минусы вариантов

#### Java + Spring Boot

- Хорошо, потому что соответствует ограничению SRS.
- Хорошо, потому что есть готовые модули для безопасности и работы с базой.
- Нейтрально, потому что требует JDK и сборщика (Maven).
- Плохо, потому что более громоздкая настройка.

#### Node.js + NestJS

- Хорошо, потому что быстрый старт и один язык с интерфейсом.
- Плохо, потому что не соответствует ограничению SRS.
- Плохо, потому что часть возможностей (планировщик, безопасность) требует дополнительных библиотек.

#### Python + Django

- Хорошо, потому что встроенная админ-панель и работа с базой.
- Плохо, потому что не соответствует ограничению SRS.
- Нейтрально, потому что для высокой нагрузки может потребоваться дополнительная настройка.

### Дополнительная информация

Ограничение зафиксировано в SRS, раздел 2.3. Решение следует пересмотреть, если ограничение SRS изменится.

## ADR-002: Хранение данных в PostgreSQL

- status: accepted
- date: 2026-11-07
- decision-makers: Огородник Е.В. (архитектор)
- consulted: Заказчик (роль в ролевой игре)
- informed: преподаватель

### Контекст и постановка задачи

Платформа хранит пользователей, усадьбы, брони и платежи. Данные о бронях и деньгах должны быть согласованными: нельзя потерять запись об оплате или сохранить две брони на одни даты (REQ-FUNC-012, REQ-REL-001). Вопрос: какую систему хранения данных использовать?

### Драйверы решения

1. Ограничение SRS (раздел 2.3): данные хранятся в реляционной базе данных PostgreSQL.
2. Надёжные транзакции (ACID) для броней и платежей.
3. Возможность запретить пересечение периодов дат на уровне базы (диапазоны дат и исключающие ограничения).
4. Бесплатность (REQ-COST-001) и простота резервного копирования (REQ-REL-003).

### Рассмотренные варианты

- PostgreSQL
- MySQL
- MongoDB

### Итог решения

Выбранный вариант: «PostgreSQL», потому что он указан в ограничениях SRS, обеспечивает строгие транзакции и позволяет запретить пересечение периодов броней самим ограничением базы данных.

### Последствия

- Хорошо, потому что пересекающиеся брони отсекаются на уровне базы, даже если в коде ошибка.
- Хорошо, потому что есть простые инструменты резервного копирования (pg_dump).
- Плохо, потому что для исключающего ограничения нужно подключить расширение btree_gist и знать особенности PostgreSQL.
- Плохо, потому что смена базы в будущем потребует переписать часть запросов и ограничений.

### Подтверждение

Проверяется инспекцией скриптов создания схемы (наличие ограничений) и тестом REQ-REL-001 (одновременные заявки на пересекающиеся даты).

### Плюсы и минусы вариантов

#### PostgreSQL

- Хорошо, потому что соответствует SRS и обеспечивает ACID.
- Хорошо, потому что поддерживает диапазоны дат и исключающие ограничения.
- Нейтрально, потому что требует установки и настройки сервера.

#### MySQL

- Хорошо, потому что широко распространена и проста.
- Плохо, потому что не соответствует ограничению SRS.
- Плохо, потому что нет прямого аналога исключающих ограничений по диапазонам.

#### MongoDB

- Хорошо, потому что гибкая структура документов.
- Плохо, потому что не соответствует SRS и данные броней и платежей хорошо ложатся в реляционную модель.
- Плохо, потому что многозаписные транзакции сложнее.

### Дополнительная информация

См. представления 004 и 008 в SDD. Решение связано с ADR-004.

## ADR-003: Приём платежей через внешний платёжный сервис

- status: accepted
- date: 2026-11-07
- decision-makers: Огородник Е.В. (архитектор)
- consulted: Заказчик (роль в ролевой игре)
- informed: преподаватель

### Контекст и постановка задачи

Система должна принимать электронный залог и оплату, а также возвращать деньги при отмене (REQ-FUNC-013, 014). При этом она не должна получать и хранить номера банковских карт (REQ-SEC-004, раздел 2.3 SRS). Вопрос: как организовать приём платежей?

### Драйверы решения

1. Безопасность: данные карт не должны попадать на сервер системы (REQ-SEC-004).
2. Требование интеграции с внешним сервисом (REQ-INT-006).
3. Трудоёмкость и юридическая простота для учебного проекта.
4. Наличие тестового режима для разработки (раздел 2.5 SRS).
5. В учебном проекте нет договора с банком или платёжным провайдером, поэтому на первом этапе настоящая оплата невозможна и нужна заглушка (имитация платёжного сервиса).

### Рассмотренные варианты

- Страница оплаты провайдера с перенаправлением
- Форма карты, встроенная в сайт (скрипт провайдера)
- Собственная обработка карт

### Итог решения

Выбранный вариант: «страница оплаты провайдера с перенаправлением», потому что данные карты вводятся только на стороне провайдера, а система получает лишь результат платежа запросом callback с проверкой подписи.

На первом этапе (учебная версия) вместо настоящего провайдера используется заглушка. Обмен с платёжным сервисом скрыт за интерфейсом PaymentGateway (создать платёж, запросить возврат). У интерфейса две реализации: MockPaymentGateway (заглушка) и реальная реализация выбранного провайдера, которая будет добавлена позже. Заглушка ведёт себя так же, как провайдер: возвращает ссылку на «страницу оплаты», на которой есть кнопки «Оплатить» и «Отклонить» (поля для ввода номера карты отсутствуют), а после нажатия отправляет в систему тот же callback с подписью на тестовом ключе. Благодаря этому бизнес-логика (статусы броней, залог, возвраты) одинакова для заглушки и для реального провайдера. Реализация выбирается настройкой (например, payment.provider=mock), страница заглушки доступна только в учебном режиме.

### Последствия

- Хорошо, потому что система не хранит и не обрабатывает данные карт, это упрощает защиту и ответственность.
- Хорошо, потому что для разработки достаточно тестового режима провайдера или заглушки.
- Хорошо, потому что при подключении настоящего провайдера меняется только одна реализация интерфейса PaymentGateway, а правила броней и возвратов остаются прежними.
- Плохо, потому что заглушка не проверяет реальные особенности провайдера (задержки, коды ошибок, особенности подписи), и их придётся проверить при подключении настоящего сервиса.
- Плохо, потому что настоящие деньги в учебной версии не списываются и не возвращаются, это нужно прямо указывать при демонстрации.
- Плохо, потому что появляется зависимость от доступности провайдера (учтено в REQ-REL-002).
- Плохо, потому что результат платежа приходит асинхронно, поэтому нужна идемпотентная обработка повторных callback.
- Нейтрально, потому что конкретный провайдер ещё не выбран.

### Подтверждение

Проверяется инспекцией (в базе и журналах нет номеров карт, REQ-SEC-004) и тестами REQ-INT-006 и REQ-REL-002 на заглушке (имитация недоступности сервиса, отклонённого и успешного платежа, возврата), а при подключении настоящего провайдера — в его тестовом режиме.

### Плюсы и минусы вариантов

#### Страница оплаты провайдера с перенаправлением

- Хорошо, потому что данные карты не попадают на сервер.
- Хорошо, потому что быстро подключается.
- Нейтрально, потому что пользователь ненадолго покидает сайт.

#### Форма карты, встроенная в сайт

- Хорошо, потому что пользователь не покидает сайт.
- Нейтрально, потому что данные карты не доходят до сервера, но страница выполняет чужой скрипт.
- Плохо, потому что сложнее интеграция и проверка безопасности.

#### Собственная обработка карт

- Плохо, потому что нарушает REQ-SEC-004.
- Плохо, потому что требует сертификации платёжной безопасности, непосильной для учебного проекта.

### Дополнительная информация

В учебной версии платёжный сервис представлен заглушкой, конкретный провайдер будет выбран позже (SDD, приложение Б). Порядок сообщений описан в представлении 006, контракт — в 005.

## ADR-004: Защита от двойных броней блокировкой и ограничением в базе

- status: accepted
- date: 2026-11-07
- decision-makers: Огородник Е.В. (архитектор)
- consulted: Заказчик (роль в ролевой игре)
- informed: преподаватель

### Контекст и постановка задачи

Двойное бронирование — главная проблема, которую должен решить продукт (REQ-FUNC-012, REQ-REL-001). Если два туриста или турист и владелец одновременно занимают одни и те же даты, система должна подтвердить только одно действие. Вопрос: как гарантировать отсутствие пересечений при параллельной работе?

### Драйверы решения

1. Надёжность: двойная бронь недопустима, надёжность важнее скорости (REQ-REL-001).
2. Защита должна работать даже при ошибке в коде.
3. Простота реализации и проверки одним разработчиком.
4. Производительность не страдает при нагрузке до 50 одновременных пользователей (REQ-PERF-001).

### Рассмотренные варианты

- Проверка только в коде приложения
- Блокировка строки усадьбы и исключающее ограничение в базе
- Оптимистичная блокировка по версии
- Максимальный уровень изоляции транзакций (SERIALIZABLE)

### Итог решения

Выбранный вариант: «блокировка строки усадьбы и исключающее ограничение в базе», потому что блокировка исключает одновременные операции над одной усадьбой, а ограничение базы данных служит независимой страховкой.

### Последствия

- Хорошо, потому что пересекающиеся брони невозможны ни при гонке запросов, ни при ошибке в коде.
- Хорошо, потому что блокируется только одна усадьба, остальные операции не замедляются.
- Плохо, потому что операции с одной усадьбой выполняются по очереди (для масштаба проекта это допустимо).
- Плохо, потому что логику нужно держать согласованной в двух местах: в сервисе и в схеме базы данных.

### Подтверждение

Тест REQ-REL-001: два одновременных подтверждения заявок на пересекающиеся даты, подтверждается только одно. Инспекция скрипта схемы: наличие исключающего ограничения.

### Плюсы и минусы вариантов

#### Проверка только в коде приложения

- Хорошо, потому что проще всего написать.
- Плохо, потому что при одновременных запросах возможна гонка и двойная бронь.

#### Блокировка строки усадьбы и исключающее ограничение в базе

- Хорошо, потому что надёжно на двух уровнях.
- Хорошо, потому что блокировка затрагивает только одну усадьбу.
- Нейтрально, потому что нужны знания о возможностях PostgreSQL.

#### Оптимистичная блокировка по версии

- Хорошо, потому что нет ожидания.
- Плохо, потому что при конфликте приходится повторять операцию, а проверка пересечения дат всё равно нужна.

#### Максимальный уровень изоляции транзакций

- Хорошо, потому что база сама обнаруживает конфликты.
- Плохо, потому что возможны отказы с повтором транзакции и общее замедление работы.

### Дополнительная информация

См. представление 008 в SDD и ADR-002 (почему PostgreSQL).

## ADR-005: Страницы формируются на сервере (Thymeleaf)

- status: proposed
- date: 2026-11-07
- decision-makers: Огородник Е.В. (архитектор)
- consulted: Заказчик (роль в ролевой игре)
- informed: преподаватель

### Контекст и постановка задачи

SRS требует веб-приложение, работающее в браузере без установки программ (раздел 2.3), адаптивное для экранов от 360 до 1920 пикселей (REQ-INT-001). Нужно решить, как строить пользовательский интерфейс: формировать страницы на сервере или сделать отдельное одностраничное приложение, общающееся с сервером по API.

### Драйверы решения

1. Простота развёртывания: одно приложение, один сервер (REQ-DIST-001).
2. Бизнес-цель: туристы должны находить усадьбы, поэтому публичные страницы каталога и карточек должны хорошо индексироваться поисковыми системами.
3. Один разработчик и ограниченное время.
4. Адаптивность и доступность (REQ-INT-001, 004).

### Рассмотренные варианты

- Thymeleaf (страницы формируются на сервере)
- React (одностраничное приложение с серверным API)

### Итог решения

Выбранный вариант: «Thymeleaf», потому что приложение остаётся единым, публичные страницы удобны для поисковых систем, а интерфейс проще сопровождать одному разработчику. Для интерактивных элементов (календарь выбора дат) допускается небольшой JavaScript внутри страниц.

### Последствия

- Хорошо, потому что не нужны отдельная сборка интерфейса, API-контракты и настройка обмена между двумя приложениями.
- Хорошо, потому что страницы сразу содержат полный текст, что полезно для поиска в интернете.
- Плохо, потому что сложные интерактивные экраны делаются менее удобно, чем на React.
- Плохо, потому что при смене подхода в будущем часть страниц придётся переписать.

### Подтверждение

Инспекция проекта (шаблоны Thymeleaf, отсутствие отдельного приложения интерфейса) и тесты REQ-INT-001 (адаптивность) и REQ-INT-004 (доступность).

### Плюсы и минусы вариантов

#### Thymeleaf

- Хорошо, потому что одно приложение и простое развёртывание.
- Хорошо, потому что публичные страницы удобны для поисковых систем.
- Нейтрально, потому что календарь потребует немного JavaScript.
- Плохо, потому что меньше возможностей для сложной интерактивности.

#### React

- Хорошо, потому что богатая интерактивность.
- Плохо, потому что нужны отдельная сборка, API и дополнительная настройка.
- Плохо, потому что поисковым системам труднее индексировать содержимое одностраничных приложений без дополнительных мер.

### Дополнительная информация

Статус «proposed» означает, что решение предложено архитектором и ещё не подтверждено заказчиком и преподавателем. После согласования статус нужно изменить на «accepted» (или «rejected»), а при выборе React обновить представления 002, 003, 005 и раздел 4 в SDD.
